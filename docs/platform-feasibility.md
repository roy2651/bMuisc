# 平台扩展可行性评估（移动端 / 小程序 / 网页版）

2026-09-22 完成的调研记录，对应 [项目规划](project-plan.md) 的 M4「平台扩展」与第 7 节待决问题。方法：四路独立调研（Tauri 移动端、微信小程序、网页版、第三方 B 站客户端先例与合规环境）加一轮交叉补漏；网页版与 CDN 结论包含当日对线上端点的直接实测（大陆住宅 IP、匿名、无 cookie）。各结论标注置信度；B 站接口、风控与各平台政策随时变化，引用注意时效。按安全约定，本文不记录带签名的媒体地址。

## 1. 结论速览

| 方向 | 结论 | 核心依据 |
| --- | --- | --- |
| 移动端（Tauri 2 iOS/Android） | ✅ 技术可行，中等工作量；**Android 直发 APK 优先**，iOS 受商店政策限制 | 本地代理可基本原样保留；后台播放需换原生播放引擎（最大重构） |
| 微信小程序 | ❌ 不建议，三重死锁 | Referer 被微信钉死无法满足 CDN；个人主体不开放音乐类目；发布版后台音频每次过审 |
| 网页版（纯浏览器） | ❌ 不可行，API 与 CDN 双硬墙（当日实测） | 外来 `Origin` 服务器层 403；音乐 CDN Referer 白名单浏览器在标准内无法满足 |
| 网页版（浏览器扩展变体） | ⚠️ 唯一技术可行变体，商店政策风险真实 | MV3 `declarativeNetRequest` 可注入 Referer / 剥 Origin；建议 AMO 或站外分发 |
| 网页版（服务器中转） | ❌ 违反本项目硬约束 + 刑事先例风险 | 媒体字节必须中转（仅中转 API 无用），落入「盗链 / 实质性替代」模式 |

风险阶梯（越靠后风险越高）：**桌面版 / APK 侧载（现状）＜ iOS 私有分发 ＜ 公网网站 + 中转 ＜ 小程序**。桌面优先、每设备独立、匿名、非托管的设计正是风险最低形态；任何扩展动作都不应突破这一形态。

## 2. 共同前提：B 站 2025–2026 执法环境

这是比平台选择更重要的横切风险，三个方向都无法回避：

- **2025-07 PiliPala**：开源 Flutter 第三方 B 站客户端（无破解、无下载、无广告）收到 B 站律师函，指控「未经授权破解接口」「实质性替代分流平台流量」「不正当竞争」，开发者停更并从含 GitHub 在内的全部平台下架（[报道](http://www.gamersky.com/tech/202507/1963539.shtml)、[分析](https://www.woshipm.com/share/6245228.html)）。
- **2026-01 bilibili-API-collect**：2 万星的公开接口文档仓库收律师函后删库并永久归档；**2026-07 BiliRoaming** 仓库清空只留律师函（[报道](https://www.donews.com/news/detail/8/6622552.html)）。bMuisc 的接口知识间接依赖该知识库，其消亡意味着后续维护成本上升。
- **司法与立法走向**：最高法指导案例 262（2025-08）将「抓取 + 重构平台内容做替代应用」定性为不正当竞争（判赔 500 万）；《反不正当竞争法》修正案 2025-10-15 生效，数据权益条款入法；最高检 2025 年典型案例（「追剧神器」聚合 App）对「伪造请求取流 + 替代平台」的运营者以侵犯著作权罪定罪（[检察通报](https://www.spp.gov.cn/spp/zdgz/202504/t20250401_692029.shtml)）。
- **B 站用户协议**明确：官方客户端是获取服务的「唯一合法渠道」（1.3），禁止脚本/爬虫未经书面许可获取服务（4.3.15）、禁止逆向（6.2）、禁止制作分发未授权第三方工具（链接协议 8.2.1.6）。
- **执法特征**：选择性、曝光度驱动——小脚本大量存活，打击的是高可见度客户端和触碰鉴权的工具；目前未检索到 B 站起诉「个人、非商业、非替代性桌面工具」的判决。

对本项目的现实对冲就是既有硬约束（**匿名访问、无批量抓取、无下载/分发、SESSDATA 只进 OS 安全存储**），加上：保持低调、不做与 B 站的关联性品牌混淆、不商业化、随时可撤。

## 3. 移动端（Tauri 2 iOS/Android）

### 3.1 框架与代理：改造成本低于预期

- Tauri 2.0（2024-10 稳定，含 iOS/Android）移动端官方支持已稳定但仍在成熟期，2025–2026 持续有移动专项修复；已有生产案例（GeoLibre 过审上架 iOS；StickyMemo 报告 90% 代码复用、iOS 包 ~8MB / Android ~4MB），但**尚无音频类播放器的公开生产案例**。
- **本地回环代理应原样保留，而不是改写为自定义 scheme**（补漏轮的实证纠偏）：自定义 scheme 在 WKWebView 走通用加载管线，每次 seek 多耗约 90–300ms；localhost HTTP 服务走原生媒体管线，是快路径（[实测记录](https://gist.github.com/uoziod/c9bdddff4e452d851d92f9a7f755fd2f)）。所需改动仅为：iOS `Info.plist` 加 `NSAllowsLocalNetworking=YES`（iOS 17+ 默认禁止明文 HTTP 到 IP），Android manifest 给 127.0.0.1 加 cleartext 例外。
- 前台自动接续不受影响：wry 默认开启 WKWebView autoplay，`ended` 自动下一首在前景可用；桌面端 M4 遗留的 WebKit 预取接续问题在移动端同样要实测。
- 若日后弃用回环改走自定义 scheme：Range/206 需自行实现，Android 侧 wry 0.42/0.44（2024 底）才修完媒体响应的重复头与崩溃问题——维持较新 Tauri/wry 版本是前提。

### 3.2 后台播放：唯一结构性重构

- WebView/JS 在两端后台都会被挂起，`<audio>` 方案在移动端后台**彻底不可用**；必须换原生播放引擎。
- 现成方案：社区插件 `tauri-plugin-native-audio`（Android: Media3 ExoPlayer + 前台服务 + MediaSession；iOS: AVPlayer + AVAudioSession `.playback` + 锁屏控制，需开启 Background Modes→Audio）。⚠️ **单一维护者的第三方 crate，不在 Tauri 官方插件列表**，无公开生产使用记录——若采用应尽早 vendor/fork，并把 JS 层设计成「遥控器」架构（引擎可替换为自写 ExoPlayer/AVPlayer 桥）。
- 这项重构意味着播放引擎从 WebView 迁到原生：现有的 engine.ts 事件模型、预取策略、错误重试语义都要在原生侧重新对齐。

### 3.3 分发路径

| 渠道 | 可行性 |
| --- | --- |
| Android APK 直发（GitHub Releases） | ✅ 风险等级与桌面版相同，是唯一不结构性抬高风险的移动路径 |
| iOS App Store | ❌ 实际关门：Guideline 5.2.2 要求「获得内容服务方的明确许可」，B 站 ToS 不授予；被投诉即下架（5.2.3 对流媒体同样适用） |
| iOS TestFlight / Ad-hoc | 演示级：外部测试 1 万人上限、构建 90 天过期；Ad-hoc 每类设备 100 台/年 |
| iOS 欧盟侧载 | 仅限欧盟且仍需 Apple 公证，不构成通用路径 |
| Google Play | 有 IP 投诉下架先例（DDA §8），比直发 APK 风险高 |

### 3.4 若启动，先行验证（spike）

1. 回环代理在 iOS / Android 实机的 seek 延迟 A/B（自定义 scheme vs localhost）。
2. `tauri-plugin-native-audio` 后台播放、锁屏控制、音频焦点实机验证（含 vendor 可行性评估）。
3. 弱网与 CDN 节点轮替在移动网络下的表现（桌面压测结论不能直接迁移）。

另注意：**移动端没有自动更新故事**——M4 的 tauri-plugin-updater 仅覆盖桌面，移动端更新只能靠重新分发或商店，路线图依赖自动更新的节奏需要区分对待。

## 4. 微信小程序：三重死锁，不建议

1. **技术死锁（硬）**：微信把所有网络请求 Referer 钉死为 `https://servicewechat.com/{appid}/{version}/page-frame.html`，官方文档明文「referer header 不可设置」「header 中不能设置 Referer」；`BackgroundAudioManager` / `InnerAudioContext` 只有 `src` 属性、无任何自定义 header API；`wx.request`/`wx.downloadFile` 也明确禁止设置 Referer。CDN 要求的 `*.bilibili.com` Referer 在小程序内**永远发不出去**，唯一能出声的架构是服务器中转——直接违反本项目硬约束。
2. **资质死锁（硬）**：音乐类目要求《网络文化经营许可证》（经营范围含音乐娱乐产品）或《信息网络传播视听节目许可证》，且**个人主体不开放音乐类目**（官方拒绝模板：「音乐属个人主体小程序未开放类目，建议申请企业主体小程序」）；小程序备案对音乐类内容要求前述许可证为前置审批。个人开发者连类目都无法建立，与代码无关。
3. **审核死锁**：`requiredBackgroundModes:['audio']` 开发/体验版即生效，**发布版每次提审都受门控**，且曾出现体验版可后台播放、正式版不行的框架性差异；运营规范 §5.6/§6.1.8 对未授权第三方 IP 内容是清退→下架→封号。

监管先例：「百灵音乐搜索器」（未授权在线音乐播放/下载）被行政处罚没收并罚款；有小程序分发未授权有声书被责令删除、罚没。技术侧还有一条：B 站自家小程序平台（miniapp.bilibili.com）沿用同样的 Referer 钉死规则——没有任何小程序生态为第三方 B 站 CDN 播放提供合规通道。

## 5. 网页版

### 5.1 双硬墙（2026-09-22 实测，大陆住宅 IP、匿名）

- **API 墙**：`api.bilibili.com` 对外来 `Origin` 返回 **HTTP 403**——是服务器端 Origin 白名单（仅回显 `https://www.bilibili.com`），不是单纯缺 CORS 头；无 `Origin` 头时同一匿名请求正常。`/x/player/playurl` 不支持 JSONP（实测回 HTML 错误页），无逃生口。结论：你域名下的页面**拿不到**签名流地址。
- **CDN 墙**：音乐 CDN（upos-sz-mirror*，音频产品实际依赖的域名族）严格 Referer 白名单，实测：浏览器 UA + 无 Referer→403；+ `Referer: https://example.com/`→403；+ `Referer: https://www.bilibili.com/`→206 正常出流。浏览器标准内无法伪造 Referer（forbidden header；Referrer-Policy 只能裁剪/清空真实来源；fetch 的 `referrer` 选项仅接受同源）；`no-referrer` 的空 Referer 行为节点相关、不可靠。
- 对照观察（不要依赖）：个别**视频**节点（cn-jstz、mcdn 系）仅校验 UA 且带 `Access-Control-Allow-Origin: *`——但音频产品依赖的音乐 CDN 是严格 Referer 白名单，宽松行为不能作为架构依据。
- 匿名档位与桌面一致：音乐接口匿名返回 192k m4a；视频端点匿名给 64kbps 音轨——网页形态也继承「匿名即 192k 上限」，登录能力受 SESSDATA 只进安全存储的约束（网页无安全存储），又一个留在桌面端的理由。
- 音频 CDN 签名地址有效期据公开文档约 3 小时（长于视频 CDN 实测的 ~25 分钟），但「每次播放前重新解析」的既有架构对两种时长都已覆盖。

### 5.2 变体对比

| 变体 | 可行性 | 关键问题 |
| --- | --- | --- |
| 纯静态站点直连 | ❌ | 上述双硬墙，任一即致命 |
| 服务器中转（API+媒体） | ❌ 不做 | 仅中转 API 无用（浏览器仍发不出 Referer），媒体字节必须过自己服务器：~0.24 元/GB（≈1.3 元/千次播放@192k）、大陆托管强制 ICP 备案、流量集中在服务器 IP 触发风控（-412/-352/WBI/v_voucher）；法律上即最高检典型案例的「盗链+实质性替代」模式，且把「每用户各自 IP」的分散风险变成集中到运营者的可归责风险——**违反硬约束，不做** |
| **浏览器扩展 + 静态前端** | ⚠️ 唯一技术可行变体 | Chrome MV3 / Firefox 113+ 的 `declarativeNetRequest.modifyHeaders` 可对 `*.bilivideo.com` 设 Referer、对 `api.bilibili.com` 剥 Origin，在浏览器内精确复刻桌面代理行为；前端组件可大量复用（Tauri 官方无 web/PWA 目标，社区 IPC mock 只是开发技巧）。风险在分发：Chrome Web Store 政策审查真实（有 2023–24 下载类扩展清理潮），建议 Firefox AMO 或站外自分发；若做，应作为独立立项而非「网页版 bMuisc」 |
| B 站官方 iframe 嵌入 | 仅作参考 | player.bilibili.com 是唯一 ToS 完全干净的网页集成，但视频向、非音频优先 |

## 6. 对本项目路线的含义

1. **M4 节奏不变**：自动更新（Windows 先行，设置页随其交付）→ 扫码登录 → 收藏同步；桌面仍是风险最低形态。
2. **移动端**：若启动，Android 先行、GitHub 直发 APK、不进商店；iOS 按 TestFlight 级评估或搁置；先做 §3.4 的三个 spike。移动端开始前应认识到它比桌面多一项结构性重构（原生播放引擎）。
3. **小程序：关闭**，不再列入待决问题。
4. **网页版**：不做服务器中转版；若未来有需求，以「浏览器扩展 + 静态前端」独立立项，站外分发。
5. 所有扩展动作的边界：匿名、无批量抓取、无下载/分发、非商业、不做与 B 站的关联性品牌混淆、保持可随时撤下的姿态。

> 时效声明：本文结论基于 2026-09-22 时点。B 站风控、各 CDN 节点策略、微信/Apple/Google 政策与司法环境都可能变化，重大决策前应复核关键事实（尤其是 §2 的执法动态与 §5.1 的实测墙）。
